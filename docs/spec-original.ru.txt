# BarberHub — система бронирования для барбершопов

## Идея проекта

Платформа, через которую клиент может:
- найти барбершоп;
- посмотреть мастеров;
- посмотреть услуги;
- увидеть свободное время;
- записаться;
- отменить или перенести запись;
- оставить отзыв.

Барбер может управлять своим расписанием, а владелец барбершопа — сотрудниками, услугами и статистикой.

## Главные роли

### CUSTOMER
Может:
- зарегистрироваться;
- войти в аккаунт;
- посмотреть барбершопы;
- посмотреть мастеров;
- посмотреть услуги;
- посмотреть свободные временные слоты;
- создать запись;
- отменить запись;
- перенести запись;
- посмотреть историю записей;
- оставить отзыв.

### BARBER
Может:
- смотреть свое расписание;
- выставлять рабочие часы;
- добавлять break;
- отмечать запись как completed;
- смотреть информацию о клиенте;
- смотреть свою статистику.

### SHOP_OWNER
Может:
- создать барбершоп;
- редактировать информацию;
- добавлять и удалять барберов;
- создавать услуги;
- назначать услуги конкретным барберам;
- управлять графиками;
- смотреть все бронирования;
- смотреть revenue/statistics.

### ADMIN
Может управлять всеми пользователями и барбершопами.

## Основные сущности БД

### users

- last_name: varchar
- email: varchar unique
- phone: varchar
- password_hash: varchar

- is_active: boolean
- created_at: timestamp

### barbershops
- id: UUID

- name: varchar
- description: text
- address: varchar
- city: varchar
- latitude: decimal
- longitude: decimal

### barbers
- id: UUID
- user_id: FK users
- shop_id: FK barbershops
- bio: text
- experience_years: integer
- rating: decimal

- Beard Trim — 3000 ₸ — 30 min

- name: varchar
- description: text

- price: decimal
- is_active: boolean

### barber_services

- barber_id

## Основная backend-логика

GET /barbers/{barber_id}/available-slots?date=2026-09-20

Backend должен:
1. получить working hours мастера;
2. получить duration услуги;
3. получить существующие appointments;
4. получить breaks;
5. вычислить свободные интервалы;
6. вернуть только доступное время.

Нужно защититься от двойного бронирования одного времени двумя клиентами.
Использовать PostgreSQL transaction, overlap checks и при необходимости row locking / exclusion constraints.
